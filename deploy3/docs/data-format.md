# 關鍵點資料格式說明

這份文件說明網站「數據」面板錄製、匯出的資料格式，回答老師的兩個問題：
- **第 5 題**：資料要用什麼格式保存，之後才能交給後端 AI 分析
- **第 6 題**：x、y、z 各代表什麼、怎麼驗證這些數字

## 怎麼錄製

1. 開啟鏡頭，按工具列的「數據」
2. 按「● 開始錄製」做動作，做完按「■ 停止錄製」（最多錄 5 分鐘）
3. 按「下載 CSV」或「下載 JSON」

檔名是錄製開始的時間，例如 `pose_20261001_153012.csv`。

## 兩種格式，用途不同

| 格式 | 給誰用 | 特色 |
|---|---|---|
| CSV | Excel、Google 試算表、Python（pandas） | 一列一格畫面，打開就能畫圖、算平均 |
| JSON | 之後的後端 AI（上傳用） | 多了裝置與設定資訊，程式讀取方便 |

兩種格式的數字完全相同，都是 **MediaPipe 原始輸出**（沒有經過畫面上的平滑處理），分析時才能自己決定要怎麼過濾。

## 座標的意思

每個點有兩組座標。

### 1. 畫面座標：`x`、`y`、`z`、`visibility`

| 欄位 | 意思 | 範圍 |
|---|---|---|
| `x` | 在畫面中的左右位置，0 是最左邊、1 是最右邊 | 通常 0～1；超出代表在畫面外（模型用猜的） |
| `y` | 在畫面中的上下位置，0 是最上面、1 是最下面 | 同上 |
| `z` | 相對深度：以**髖部中心**為 0，**越小（負越多）越靠近鏡頭** | 大約和 x 同一個比例尺 |
| `visibility` | 模型認為這個點真的看得到的機率 | 0～1；網站畫面上低於 0.65 的點不畫 |

- 座標是**鏡頭原始畫面**，沒有鏡像。前鏡頭的畫面在網站上有鏡像，但錄下來的資料沒有。
- 「左、右」是被拍攝者本人的左右，例如 `left_knee` 一定是本人的左膝。
- `z` 是模型從單張畫面推估的，不是真的量出來的距離，所以要做下面的驗證實驗。

### 2. 真實世界座標：`wx`、`wy`、`wz`（單位：公尺）

MediaPipe 另外推估一組以**公尺**為單位的 3D 座標，原點是**髖部中心**：
- `wx`：左右
- `wy`：上下（往下為正）
- `wz`：前後（越小越靠近鏡頭）

這組座標**理論上不受人站多遠影響**（站遠站近，膝蓋到腳踝都大約是同樣的公尺數），適合用來比較**動作幅度**。

> **注意：前後深度（`wz`）的誤差很大。** 我們用一張雙腿伸直、身體與鏡頭平行的照片實測，伸直的腿用畫面座標算是 174°，用公尺座標算卻是 152°。所以網站上顯示的**關節角度是用畫面座標（2D）計算**，並建議從**側面**拍攝深蹲等動作。公尺座標仍完整保存，可以用下面的實驗 D、E 驗證後再決定要不要使用。

## CSV 欄位

| 欄位 | 說明 |
|---|---|
| `frame` | 第幾格（從 0 開始） |
| `time_ms` | 距離開始錄製幾毫秒 |
| `detected` | 這一格有沒有偵測到人（1 有、0 沒有；沒有時座標欄位空白） |
| `nose_x`、`nose_y`、`nose_z`、`nose_vis` … | 33 個點的畫面座標，共 132 欄 |
| `nose_wx`、`nose_wy`、`nose_wz` … | 33 個點的公尺座標，共 99 欄 |

點的名稱和網站上的編號對照表相同（`js/landmarks.js`），例如 `left_knee` 是 25 號。共 234 欄。

## JSON 結構

```json
{
  "format": "ai-sport-pose",
  "version": 1,
  "meta": {
    "app": "AI 智慧運動分析系統",
    "model": "pose_landmarker_lite",
    "computeMode": "GPU",
    "videoWidth": 640,
    "videoHeight": 480,
    "displayMirrored": true,
    "userAgent": "…",
    "startedAt": "2026-10-01T07:30:12.000Z"
  },
  "landmarkNames": ["NOSE", "LEFT_EYE_INNER", "…"],
  "fields": { "landmarks": ["x", "y", "z", "visibility"], "world": ["x", "y", "z"] },
  "frames": [
    { "t": 0,  "landmarks": [[0.512, 0.301, -0.402, 0.999], "…共 33 點"], "world": [[0.01, -0.62, -0.25], "…"] },
    { "t": 50, "landmarks": null, "world": null }
  ]
}
```

- `t`：距離開始錄製幾毫秒；`landmarks` 為 `null` 代表這一格沒偵測到人
- `version`：之後格式如果改變就加 1，後端可以依版本號讀取

## 為什麼這樣設計（給後端 AI 的考量）

1. **只傳關鍵點，不傳影片**：每格約 1.9 KB，一分鐘約 2～3 MB（每秒 20～30 格），同長度的影片通常要數十 MB；也不會把使用者的臉傳出去，隱私比較好
2. **保留原始資料**：平滑、過濾、算角度都在後端做，之後換方法時不用重錄
3. **畫面座標與公尺座標都保留**：畫面座標可以和影片對照、計算角度；公尺座標保留給之後驗證與研究
4. **沒偵測到的格子也記錄**：時間軸才是連續的，看得出中間斷掉多久

## 畫面上的點與錄製資料的差別

錄製的資料是 MediaPipe 的原始輸出，**沒有經過任何過濾**；畫面上畫出來的點則多了兩道處理：

1. 平滑（`js/smooth.js`）：讓點不抖動
2. 擋掉鬼點（`js/ghost.js`）：模型有時會腦補出不存在的手腳，或在人離開畫面後留下一副越縮越小的骨架，而且可信度常常很高（0.8～0.96）。所以另外加三道檢查：出現要穩定（可信度連續 0.08 秒 ≥ 0.75）、骨架鏈（手腕要手肘也看得到才畫）、塌縮保護（身體大小 0.3 秒內縮小 3 成以上視為鬼骨架）

分析錄製資料時，如果也想排除鬼點，可以用同樣的規則處理。

鬼點模擬測試（MediaPipe 官方測試照片做成晃動、走近走遠、走出畫面、變暗、加雜訊的連續畫面，各 240 格；以 heavy 模型的偵測結果當正確答案，畫出位置偏離超過畫面高度 10% 算錯）：

| 情境 | 錯位點／格（改前 → 改後） | 漏畫主要關節（改前 → 改後） |
|---|---|---|
| 鏡頭很近，只拍到頭和胸 | 1.64 → 0.23 | 0.2% → 2.2% |
| 人走出畫面再回來 | 4.87 → 1.48 | 7.2% → 26.4%（多半是半個身體在畫面外時邊緣的關節） |
| 走近走遠、光線暗、沒有人 | 幾乎 0 → 幾乎 0 | 最多增加約 5%（身體部位剛進畫面時，點會晚約 0.1 秒出現） |

## 拍攝方向與角度準確度

角度用畫面上的 2D 座標計算，所以**拍攝方向**會影響準確度。深蹲、伏地挺身這類前後彎的動作，從側面拍才準。

`js/view.js` 用「肩寬＋髖寬」和「軀幹長度」的比值判斷拍攝方向：正側面時左右肩、左右髖幾乎重疊，比值接近 0；越轉向正面越大，真人正面約 0.5。數據面板上會顯示目前的判斷和比值。

用 3D 合成骨架模擬（身體比例取自 MediaPipe 在真人照片上的輸出），轉到不同拍攝角度、做不同深度的深蹲，以正側面拍到的角度當作正確答案：

| 拍攝角度（0° = 正側面） | 比值 | 膝蓋角度最大誤差 | 髖部角度最大誤差 | 判斷結果 |
|---|---|---|---|---|
| 0° | 0.00 | 0° | 0° | 側面 |
| 20° | 0.17 | 4° | 6° | 側面 |
| 30° | 0.26 | 9° | 12° | 斜側面 |
| 40° | 0.33 | 16° | 20° | 正面 |
| 60° | 0.44 | 40° | 47° | 正面 |
| 90°（正面） | 0.51 | 106° | 90° | 正面 |

2,223 種組合（拍攝角度 × 深蹲深度 × 前傾程度 × 小腿角度）的總結：判斷為「側面」時膝蓋角度誤差**最大 4.1°**；「斜側面」最大 12.3°；「正面」中位數 24°、最大 116°。

另外兩個相關的處理（`js/angles.js`）：

- **肢體太短不給角度**：大腿、前臂等朝著鏡頭伸出時，在畫面上只剩一小段，算出來的角度沒有意義。肢體在畫面上不到應有長度的一半（或短於 12 像素）時不給角度，畫面上顯示「—」。正面拍深蹲蹲到大腿接近水平時會觸發；但正面半蹲時大腿還不夠短，擋不到，所以主要還是要靠拍攝方向判斷
- **有方向的角度**：一般角度只有 0～180°，膝蓋往前彎 170° 和往後反折 10°（190°）看起來一樣。側面拍時用「鼻子在耳朵前面、腳尖在腳跟前面」判斷人面向哪邊，再看關節往哪邊彎，往後反折、後伸時顯示超過 180°（例如弓箭步後腳的髖約 200°）。目前顯示在數據面板，之後做動作判斷時使用

限制：以上是用合成骨架算出來的，真人側面拍的實測要等錄影資料（見下面的驗證實驗 G）。

## 骨架跟手程度（往前預測）

AI 拿某一格畫面去算，算完才畫出來；這段時間人又動了一點，骨架看起來會拖在身體後面。`js/predict.js` 用平滑程式算出的速度，把**畫出來的位置**往前推「從拍到畫出來經過的時間」（最多 150 毫秒）。角度、深蹲判斷、錄製資料都用沒預測的數字。

速度很小時（只是雜訊）不預測（死區：每秒 40 像素以下不推、120 像素以上完全推），站著不動時點才不會飄。

用 3D 合成深蹲模擬（加上畫面雜訊，對照當下真實位置；單位：像素）：

| 情境 | 動作中：不預測 → 預測 | 靜止時：不預測 → 預測 | 靜止抖動：不預測 → 預測 |
|---|---|---|---|
| 每秒 30 格、延遲 40 ms | 6.8 → 3.0 | 1.4 → 1.4 | 0.3 → 0.4 |
| 每秒 15 格、延遲 80 ms | 11.8 → 6.0 | 2.2 → 2.0 | 0.4 → 0.4 |
| 快速深蹲、每秒 30 格 | 9.4 → 4.7 | 1.2 → 1.6 | 0.3 → 0.4 |

網址加 `?predict=0` 可以關掉預測對照。

**取捨：突然停住時會短暫衝過頭。** 預測是用「還在動」的資料往前推，人如果在那一瞬間剛好停住，骨架會衝過頭一點，約 0.1～0.3 秒內回到原位（等於把「動作中落後」換成「停住時超前」，量差不多）。最極端的情況（瞬間從等速變成完全靜止）模擬結果：

| 移動速度（每秒 30 格） | 不預測：動作中落後 | 預測：停住時衝過頭 |
|---|---|---|
| 每秒 300 像素 | 15 | 12.6 |
| 每秒 600 像素 | 27 | 24.7 |

真人停下前會先減速，實際上小很多：上面的合成深蹲（會減速）裡，預測的最大誤差反而比不預測小（每秒 30 格：4.1 vs 8.0 像素）。也試過「最新一格變慢就少推一點」的做法，衝過頭只少約 1 成、動作中誤差卻變大，所以沒有採用。

## 驗證實驗建議（第 6 題）

用來確認 x、y、z 的數字是否可信。每個實驗都錄一段，下載 CSV 後用 Excel 畫折線圖。

| 實驗 | 怎麼做 | 預期結果 |
|---|---|---|
| A. 靜止穩定度 | 全身入鏡站著不動 10 秒 | 各點的 x、y 幾乎是一條水平線；可算標準差當作「雜訊大小」 |
| B. x、y 方向 | 只把右手慢慢往右平舉，再往上舉 | 右腕的 x、y 隨動作平順地變化，其他點不動 |
| C. z 深度方向 | 側身站，右手往鏡頭方向伸直再收回 | `right_wrist_z` 伸出時變小（負更多）、收回時變大 |
| D. 公尺座標的尺度 | 量自己大腿長度（髖到膝），站遠、站近各錄一次 | `wx/wy/wz` 算出的髖到膝距離接近實際長度，且兩次差不多 |
| E. 鏡頭距離影響 | 同一個深蹲動作，在 2 公尺、3 公尺各做一次 | 畫面座標的幅度會變，公尺座標的幅度應該差不多 |
| F. 裝置差異 | 同一個人、同一個動作，用筆電和手機各錄一次 | 比較 A 的雜訊大小與 `visibility`，找出哪種裝置比較穩 |
| G. 拍攝方向 | 同一個深蹲，鏡頭放在正側面、斜 30°、正面各錄一次，打開數據面板看判斷結果 | 正側面判斷為「側面」、正面判斷為「正面」；三次的最低膝蓋角度，正側面最接近實際 |

每個實驗錄完後，可以把 JSON 丟進網站的「錄製資料重播分析」（`replay.html`），直接看角度曲線、拍攝方向和抖動大小，不用自己用 Excel 畫圖。

實驗 D、E 最重要：如果公尺座標在不同距離下都一致、深度誤差可接受，之後就能改用 3D 計算角度，不再限制只能從側面拍。
