# 關鍵點資料格式說明

這份文件說明網站「數據」面板錄製、匯出的資料格式，回答老師的兩個問題：
- **第 5 題**：資料要用什麼格式保存，之後才能交給後端 AI 分析
- **第 6 題**：x、y、z 各代表什麼、怎麼驗證這些數字

## 怎麼錄製

1. 開啟鏡頭，按工具列的「數據」
2. 按「● 開始錄製」做動作，做完按「■ 停止錄製」（一次最多錄幾分鐘可以選 5、10、15、20 分鐘，預設 5 分鐘；剩 30 秒、錄滿自動停止時畫面中間會出現大字並嗶一聲。建議一個動作錄一段）
3. 按「下載 CSV」或「下載 JSON」

檔名是錄製開始的時間，例如 `pose_20261001_153012.csv`。

10/20 起每一段停止錄製後自動存進這支手機的「錄製檔」（瀏覽器的 IndexedDB，`js/data/library.js`），可以一段一段下載、勾選的一次下載，或壓縮成一個 zip（`recordings_日期_時間.zip`，裡面就是一個個 JSON，deflate 壓縮，一般解壓縮軟體都打得開）。

實測模式（首頁的「實測模式」卡片，10/20；10/21 從進階設定拿出來）錄的一組也存進錄製檔（可以設定每組馬上下載），檔名前面多了受測者代號、動作、這組要做的：`test_<代號>_<動作>_<這組要做的>_<日期>_<時間>.json`，例如 `test_A_squat_heel_20261021_153012.json`（受測者 A、深蹲、故意腳跟離地）。這組要做的是 `good`（做對）或錯誤代號（見 `js/analysis/form.js`：`lean` 上身前傾、`heel` 腳跟離地、`sag` 塌腰、`pike` 屁股太高、`knee` 前膝超過腳尖）。同一組錄了好幾次時，以時間最晚的為準。

## 兩種格式，用途不同

| 格式 | 給誰用 | 特色 |
|---|---|---|
| CSV | Excel、Google 試算表、Python（pandas） | 一列一格畫面，打開就能畫圖、算平均 |
| JSON | 之後的後端 AI（上傳用） | 多了裝置與設定資訊，程式讀取方便 |

兩種格式的數字完全相同，都是 **MediaPipe 原始輸出**（沒有經過畫面上的平滑處理），分析時才能自己決定要怎麼過濾。

## 座標的意思

每個點有兩組座標。

### 1. 畫面座標：`x`、`y`、`z`、`visibility`

| 欄位 | 意思 | 範圍 |
|---|---|---|
| `x` | 在畫面中的左右位置，0 是最左邊、1 是最右邊 | 通常 0～1；超出代表在畫面外（模型用猜的） |
| `y` | 在畫面中的上下位置，0 是最上面、1 是最下面 | 同上 |
| `z` | 相對深度：以**髖部中心**為 0，**越小（負越多）越靠近鏡頭** | 大約和 x 同一個比例尺 |
| `visibility` | 模型認為這個點真的看得到的機率 | 0～1；網站畫面上低於 0.65 的點不畫 |

- 座標是**鏡頭原始畫面**，沒有鏡像。前鏡頭的畫面在網站上有鏡像，但錄下來的資料沒有。
- 「左、右」是被拍攝者本人的左右，例如 `left_knee` 一定是本人的左膝。
- `z` 是模型從單張畫面推估的，不是真的量出來的距離，所以要做下面的驗證實驗。

### 2. 3D 座標（真實世界座標）：`wx`、`wy`、`wz`（檔案裡的單位：公尺）

MediaPipe 另外推估一組以**公尺**為單位的 3D 座標，原點是**髖部中心**：
- `wx`：左右
- `wy`：上下（往下為正）
- `wz`：前後（越小越靠近鏡頭）

**單位：** 網站畫面上（重播分析的「3D 檢查」）一律換成**公分**顯示；下載的檔案維持公尺，**乘以 100 就是公分**。檔案維持公尺，是因為這是 MediaPipe 原本的單位，以前錄的檔案也都是公尺，單位一致才不會在分析時搞混。換成公分不會比較精確：檔案記到公尺的小數第 4 位（0.1 公釐），準不準取決於 AI 估得準不準（目前同一個人換裝置，腿長差 2 公分以內；準不準要用捲尺對照，見實驗 D）。

這組座標**理論上不受人站多遠影響**（站遠站近，膝蓋到腳踝都大約是同樣的公尺數），適合用來比較**動作幅度**。

> **注意：前後深度（`wz`）的誤差很大。** 我們用一張雙腿伸直、身體與鏡頭平行的照片實測，伸直的腿用畫面座標算是 174°，用 3D 座標算卻是 152°。所以網站上顯示的**關節角度是用畫面座標（2D）計算**，並建議從**側面**拍攝深蹲等動作。3D 座標仍完整保存，另外也存一份處理過的（平滑＋骨頭長度限制，見「3D 座標的處理」），可以用下面的實驗 D、E、H 驗證後再決定要不要使用。

## CSV 欄位

| 欄位 | 說明 |
|---|---|
| `frame` | 第幾格（從 0 開始） |
| `time_ms` | 距離開始錄製幾毫秒 |
| `detected` | 這一格有沒有偵測到人（1 有、0 沒有；沒有時座標欄位空白） |
| `nose_x`、`nose_y`、`nose_z`、`nose_vis` … | 33 個點的畫面座標，共 132 欄 |
| `nose_wx`、`nose_wy`、`nose_wz` … | 33 個點的 3D 座標，共 99 欄 |
| `nose_sx`、`nose_sy`、`nose_sz`、`nose_svis`、`nose_seen` … | 33 個點**平滑後**的畫面座標（和畫面上的骨架相同），共 165 欄；`seen` 為 1 代表畫面上有畫出這個點、0 代表被擋鬼點擋掉或看不到；沒有人或整副被判斷成鬼骨架時空白 |

| `nose_swx`、`nose_swy`、`nose_swz` … | 33 個點**處理過的 3D 座標**（平滑＋骨頭長度限制，見下方「3D 座標的處理」），共 99 欄 |

點的名稱和網站上的編號對照表相同（`js/skeleton/landmarks.js`），例如 `left_knee` 是 25 號。共 498 欄。新的欄位都加在最後面，前面 234 欄和以前完全相同，舊的分析程式（只讀前面的欄位）不用改。

## JSON 結構

```json
{
  "format": "ai-sport-pose",
  "version": 1,
  "meta": {
    "app": "AI 智慧運動分析系統",
    "model": "pose_landmarker_lite",
    "modelChoice": "lite",
    "computeMode": "GPU",
    "videoWidth": 640,
    "videoHeight": 480,
    "cameraFrameRate": 30,
    "fpsChoice": 30,
    "aiMsPerFrame": 12,
    "displayMirrored": true,
    "userAgent": "…",
    "startedAt": "2026-10-01T07:30:12.000Z"
  },
  "landmarkNames": ["NOSE", "LEFT_EYE_INNER", "…"],
  "fields": { "landmarks": ["x", "y", "z", "visibility"], "world": ["x", "y", "z"], "smoothed": ["x", "y", "z", "visibility", "seen"], "stableWorld": ["x", "y", "z"] },
  "frames": [
    { "t": 0,  "landmarks": [[0.512, 0.301, -0.402, 0.999], "…共 33 點"], "world": [[0.01, -0.62, -0.25], "…"], "smoothed": [[0.512, 0.301, -0.402, 0.999, 1], "…"], "stableWorld": [[0.01, -0.62, -0.24], "…"] },
    { "t": 50, "landmarks": null, "world": null, "smoothed": null, "stableWorld": null }
  ]
}
```

- `t`：距離開始錄製幾毫秒；`landmarks` 為 `null` 代表這一格沒偵測到人
- `smoothed`：平滑後的點（和畫面上的骨架、數據面板「平滑後」的數字相同）；`seen` 為 1 代表畫面上有畫出這個點
- `stableWorld`：處理過的 3D 座標（見下方「3D 座標的處理」）
- 2026-10 以前錄的檔案沒有 `smoothed`、`stableWorld`
- `meta.cameraFrameRate`：鏡頭設定的每秒格數（瀏覽器回報的，不知道時是 0；每秒格數選 60 以上時，用來確認鏡頭有沒有真的給那麼多格）。實際錄到每秒幾格看 `t`，因為 AI 算不完的格子會跳過；2026-10-12 以前的檔案沒有這個欄位
- `meta.workout`：選的運動模式（`free` 自由、`squat`、`pushup`、`plank`、`lunge`），重播分析頁用它分析次數和錯誤；2026-10-14 以前的檔案沒有這個欄位
- `meta.calibration`：個人校正的結果 `{ knee, tilt }`（站直時的膝蓋角度、手機歪了幾度：站直時「髖部中心 → 兩腳踝中間」的線和畫面垂直線的夾角），還沒校正時是 `null`；重播分析沿用這個結果（沒有的話從錄影裡站直不動的那段自己校正）；2026-10-14 以前的檔案沒有這個欄位
- `meta.modelChoice`：使用者選的模型（`"lite"`、`"full"` 或 `"auto"` 自動；實際用的是 `model`，錄製中不會換）；2026-10-13 以前的檔案沒有這個欄位
- `meta.fpsChoice`：使用者選的每秒格數（30、60、90、120 或 `"auto"` 自動；自動時錄製中不會換格數，實際的格數看 `cameraFrameRate`）；2026-10-13 以前的檔案沒有這個欄位
- `meta.aiMsPerFrame`：開始錄製前 AI 每格算幾毫秒（最近 30 格的中位數，還沒算過時是 `null`），用來比較不同手機、不同模型的速度；2026-10-13 以前的檔案沒有這個欄位
- `meta.pauses`：錄製中按過暫停才有（10/20）。`[{ "from": 2010, "to": 5010 }]`：每一次暫停從幾毫秒到幾毫秒（和每一格的 `t` 同一個起點）。暫停時不錄，所以 `t` 會跳一段（是真的時間，不是接起來的）；畫面上「已錄」和錄製上限都不算暫停的時間
- `meta.test`：只有實測模式錄的才有。`{ "subject": "A", "condition": "heel", "reps": 5 }`：受測者代號（只有英文大寫和數字）、這組要做的（和檔名一樣）、要做幾下（棒式是 `"seconds": 30` 撐幾秒）。讀檔時代號、這組要做的對不上（例如被改過）就當成一般錄製檔（`js/data/test-mode.js` 的 `testInfo`）

## 3D 座標的處理（`js/skeleton/world.js`）

只有一支鏡頭時，前後深度是 AI 猜的：雜訊比左右上下大很多，還會慢慢飄、偶爾跳開。錄製時除了原始的 `wx/wy/wz`，另外存一份處理過的 `swx/swy/swz`：

1. **平滑**：x、y、z 各用一個 One Euro Filter（和畫面上骨架的平滑同一種方法）
2. **骨頭長度限制**：大腿、小腿、上臂、前臂的長度不會變。量到的 3D 長度不對時，保留左右上下、只調整深度差，往估計的骨頭長度（最近 4 秒的中間值）拉回一半；**只在深度方向很明確時才修正**

用合成深蹲（有真實 3D 位置）加上深度雜訊、飄移、偶爾跳開模擬，3 種雜訊大小 × 3 種速度 × 3 種拍攝角度 × 20 組亂數，共 540 組：

| | 平均位置誤差 | 平均 3D 膝蓋角度誤差 |
|---|---|---|
| 原始 | 4.55 公分 | 9.67° |
| 處理過 | 3.51 公分（少 23%） | 6.94°（少 28%） |

540 組沒有任何一組比原始差。也試過「每一格都把長度完整拉回」：骨頭長度看起來很穩，但位置、角度反而**更不準**（膝角多 2～6°）——肢體和鏡頭平行時深度差接近 0，往前還是往後只是雜訊，硬拉會推錯邊。所以**「骨頭長度很穩」不代表比較準**，要用有標準答案的方法驗證（下方實驗 D）。

模擬的雜訊是依經驗設定的，真實錄影的誤差可能不同（例如整體偏差），請用實驗 D 確認後再決定要用哪一份。
- `version`：之後格式如果改變就加 1，後端可以依版本號讀取

## 雲端（Firestore）的資料格式

打開「雲端同步」後（[firebase-setup.md](firebase-setup.md)），每次運動的總結存成一筆：`users/{這台裝置的匿名帳號}/sessions/{動作-開始時間}`，例如 `users/Xa81…/sessions/squat-1792300000000`。
只有下面這些欄位（白名單在 `js/cloud/sync.js`，雲端的安全規則 `firestore.rules` 用同一套條件檢查），沒有影像、沒有關鍵點座標。

| 欄位 | 型別 | 意思 |
|---|---|---|
| `v` | 整數 | 格式版本，目前是 1（欄位改了就加 1） |
| `workout` | 文字 | `squat`、`pushup`、`lunge`、`plank` |
| `date` | 整數 | 開始的時間（1970 年起的毫秒），也是代號的一部分 |
| `minutes` | 數字 | 這次運動幾分鐘 |
| `count` | 整數 | 幾下（棒式：撐了幾次），至少 1 |
| `clean` | 整數 | 沒有偵測到錯誤的有幾下 |
| `errors` | 對照表 | 錯誤代號 → 幾下有這個錯誤，例如 `{ "lean": 2, "heel": 1 }`；代號見 `js/analysis/form.js` |
| `savedAt` | 時間 | 存進雲端的時間（伺服器的時間） |
| 計次的動作 | | |
| `good`、`close`、`shallow` | 整數 | 到位、再低一點、太淺各幾下（加起來等於 `count`） |
| `best`、`average` | 數字 | 最低、平均角度（°） |
| `tempo` | 數字 | 每一下平均幾秒 |
| `similarity` | 整數或 null | 和示範動作的平均相似度（0～100）；沒算出來是 null |
| 棒式 | | |
| `seconds` | 整數清單 | 每一次撐了幾秒（個數等於 `count`） |
| `best`、`total` | 數字 | 最久、總共幾秒 |

這台裝置上的紀錄（首頁「運動紀錄」）另外有 `peaks`：每種錯誤最嚴重的一下量到多少（度或 %，例如 `{ "lean": 62 }`），總結用來說出原因；**不上傳雲端**（不在白名單裡）。計次的動作（深蹲、伏地挺身、弓箭步）填了「實際做了幾下」時另外有 `actual`（0～999 的整數），總結用來算計次準確率；一樣**不上傳雲端**。

## 為什麼這樣設計（給後端 AI 的考量）

1. **只傳關鍵點，不傳影片**：每格約 1.9 KB，一分鐘約 2～3 MB（每秒 20～30 格），同長度的影片通常要數十 MB；也不會把使用者的臉傳出去，隱私比較好
2. **保留原始資料**：平滑、過濾、算角度都可以在後端重做，之後換方法時不用重錄；另外也存一份網站當下平滑後的結果，方便直接比較「原始 vs 平滑後」（模擬：站著不動時，左膝 x 每格的變化從 2.05 像素降到 0.39 像素）
3. **畫面座標與 3D 座標都保留**：畫面座標可以和影片對照、計算角度；3D 座標保留給之後驗證與研究
4. **沒偵測到的格子也記錄**：時間軸才是連續的，看得出中間斷掉多久

## 畫面上的點與錄製資料的差別

錄製的資料是 MediaPipe 的原始輸出，**沒有經過任何過濾**；畫面上畫出來的點則多了兩道處理：

1. 平滑（`js/skeleton/smooth.js`）：讓點不抖動
2. 擋掉鬼點（`js/skeleton/ghost.js`）：模型有時會腦補出不存在的手腳，或在人離開畫面後留下一副越縮越小的骨架，而且可信度常常很高（0.8～0.96）。所以另外加三道檢查：出現要穩定（可信度連續 0.08 秒 ≥ 0.75）、骨架鏈（手腕要手肘也看得到才畫）、塌縮保護（身體大小 0.3 秒內縮小 3 成以上視為鬼骨架，而且軀幹長和肩寬＋髖寬要都縮小才算，正面轉側面時只有寬度變小，不會被誤判；之後大小穩定 1 秒沒有繼續縮小，就當作真人恢復顯示，例如人走到鏡頭前調整手機再快速退回原位時，不會一直被當作沒有人）。AI 偶爾漏掉一兩格（0.2 秒以內）時，擋鬼點和拍攝方向接著用、不重新確認，畫面上也保留上一格的骨架，不會閃一下或跳出「未偵測到人體」；6 種真實情境中，預設的輕量模型錯位點因此少了 1/3、閃爍減半

分析錄製資料時，如果也想排除鬼點，可以用同樣的規則處理。

鬼點模擬測試（MediaPipe 官方測試照片做成晃動、走近走遠、走出畫面、變暗、加雜訊的連續畫面，各 240 格；以 heavy 模型的偵測結果當正確答案，畫出位置偏離超過畫面高度 10% 算錯）：

| 情境 | 錯位點／格（改前 → 改後） | 漏畫主要關節（改前 → 改後） |
|---|---|---|
| 鏡頭很近，只拍到頭和胸 | 1.64 → 0.23 | 0.2% → 2.2% |
| 人走出畫面再回來 | 4.87 → 1.48 | 7.2% → 26.4%（多半是半個身體在畫面外時邊緣的關節） |
| 走近走遠、光線暗、沒有人 | 幾乎 0 → 幾乎 0 | 最多增加約 5%（身體部位剛進畫面時，點會晚約 0.1 秒出現） |

## 拍攝方向與角度準確度

角度用畫面上的 2D 座標計算，所以**拍攝方向**會影響準確度。深蹲、伏地挺身這類前後彎的動作，從側面拍才準。

`js/analysis/view.js` 用「肩寬＋髖寬」和「軀幹長度」的比值判斷拍攝方向：正側面時左右肩、左右髖幾乎重疊，比值接近 0；越轉向正面越大，真人正面約 0.5。數據面板上會顯示目前的判斷和比值。

用 3D 合成骨架模擬（身體比例取自 MediaPipe 在真人照片上的輸出），轉到不同拍攝角度、做不同深度的深蹲，以正側面拍到的角度當作正確答案：

| 拍攝角度（0° = 正側面） | 比值 | 膝蓋角度最大誤差 | 髖部角度最大誤差 | 判斷結果 |
|---|---|---|---|---|
| 0° | 0.00 | 0° | 0° | 側面 |
| 20° | 0.17 | 4° | 6° | 側面 |
| 30° | 0.26 | 9° | 12° | 斜側面 |
| 40° | 0.33 | 16° | 20° | 正面 |
| 60° | 0.44 | 40° | 47° | 正面 |
| 90°（正面） | 0.51 | 106° | 90° | 正面 |

2,223 種組合（拍攝角度 × 深蹲深度 × 前傾程度 × 小腿角度）的總結：判斷為「側面」時膝蓋角度誤差**最大 4.1°**；「斜側面」最大 12.3°；「正面」中位數 24°、最大 116°。

另外兩個相關的處理（`js/analysis/angles.js`）：

- **肢體太短不給角度**：大腿、前臂等朝著鏡頭伸出時，在畫面上只剩一小段，算出來的角度沒有意義。肢體在畫面上不到應有長度的一半（或短於 12 像素）時不給角度，畫面上顯示「—」。「應有長度」用四肢互相比較（一兩段變短不影響），不和軀幹比：真實錄影發現手機放得比較高時，越下面的部位在畫面上縮得越多，和軀幹比會讓站直的膝蓋也不給角度。正面拍深蹲蹲到大腿接近水平時會觸發；但正面半蹲時大腿還不夠短，擋不到，所以主要還是要靠拍攝方向判斷
- **有方向的角度**：一般角度只有 0～180°，膝蓋往前彎 170° 和往後反折 10°（190°）看起來一樣。側面拍時用「鼻子在耳朵前面、腳尖在腳跟前面」判斷人面向哪邊，再看關節往哪邊彎，往後反折、後伸時顯示超過 180°（例如弓箭步後腳的髖約 200°）。目前顯示在數據面板，之後做動作判斷時使用

限制：以上是用合成骨架算出來的，真人側面拍的實測要等錄影資料（見下面的驗證實驗 G）。

## 骨架跟手程度（往前預測）

AI 拿某一格畫面去算，算完才畫出來；這段時間人又動了一點，骨架看起來會拖在身體後面。`js/skeleton/predict.js` 用平滑程式算出的速度，把**畫出來的位置**往前推「從拍到畫出來經過的時間」（最多 150 毫秒）。角度、深蹲判斷、錄製資料都用沒預測的數字。

速度很小時（只是雜訊）不預測（死區：每秒 40 像素以下不推、120 像素以上完全推），站著不動時點才不會飄。

用 3D 合成深蹲模擬（加上畫面雜訊，對照當下真實位置；單位：像素）：

| 情境 | 動作中：不預測 → 預測 | 靜止時：不預測 → 預測 | 靜止抖動：不預測 → 預測 |
|---|---|---|---|
| 每秒 30 格、延遲 40 ms | 6.8 → 3.0 | 1.4 → 1.4 | 0.3 → 0.4 |
| 每秒 15 格、延遲 80 ms | 11.8 → 6.0 | 2.2 → 2.0 | 0.4 → 0.4 |
| 快速深蹲、每秒 30 格 | 9.4 → 4.7 | 1.2 → 1.6 | 0.3 → 0.4 |

網址加 `?predict=0` 可以關掉預測對照。

**取捨：突然停住時會短暫衝過頭。** 預測是用「還在動」的資料往前推，人如果在那一瞬間剛好停住，骨架會衝過頭一點，約 0.1～0.3 秒內回到原位（等於把「動作中落後」換成「停住時超前」，量差不多）。最極端的情況（瞬間從等速變成完全靜止）模擬結果：

| 移動速度（每秒 30 格） | 不預測：動作中落後 | 預測：停住時衝過頭 |
|---|---|---|
| 每秒 300 像素 | 15 | 12.6 |
| 每秒 600 像素 | 27 | 24.7 |

真人停下前會先減速，實際上小很多：上面的合成深蹲（會減速）裡，預測的最大誤差反而比不預測小（每秒 30 格：4.1 vs 8.0 像素）。也試過「最新一格變慢就少推一點」的做法，衝過頭只少約 1 成、動作中誤差卻變大，所以沒有採用。

## 驗證實驗建議（第 6 題）

用來確認 x、y、z 的數字是否可信。每個實驗都錄一段，下載 CSV 後用 Excel 畫折線圖。

| 實驗 | 怎麼做 | 預期結果 |
|---|---|---|
| A. 靜止穩定度 | 全身入鏡站著不動 10 秒 | 各點的 x、y 幾乎是一條水平線；可算標準差當作「雜訊大小」 |
| B. x、y 方向 | 只把右手慢慢往右平舉，再往上舉 | 右腕的 x、y 隨動作平順地變化，其他點不動 |
| C. z 深度方向 | 側身站，右手往鏡頭方向伸直再收回 | `right_wrist_z` 伸出時變小（負更多）、收回時變大 |
| D. 3D 座標的尺度 | 用捲尺量自己大腿長度（髖到膝），做幾下深蹲，站遠、站近各錄一次 | 分別用原始 `wx/wy/wz` 和處理過的 `swx/swy/swz` 算髖到膝的距離：哪一份的平均最接近捲尺量的長度、兩次距離的結果最一致，就比較準（只看「長度穩不穩」不夠，要和捲尺比） |
| E. 鏡頭距離影響 | 同一個深蹲動作，在 2 公尺、3 公尺各做一次 | 畫面座標的幅度會變，3D 座標的幅度應該差不多 |
| F. 裝置差異 | 同一個人、同一個動作，用筆電和手機各錄一次 | 比較 A 的雜訊大小與 `visibility`，找出哪種裝置比較穩 |
| G. 拍攝方向 | 同一個深蹲，鏡頭放在正側面、斜 30°、正面各錄一次，打開數據面板看判斷結果 | 正側面判斷為「側面」、正面判斷為「正面」；三次的最低膝蓋角度，正側面最接近實際 |
| H. 3D 膝蓋角度 | 兩支手機同時錄同一組深蹲：一支放正側面、一支放正面 | 側面那支的畫面角度當標準答案；正面那支分別用原始 `wx/wy/wz` 和處理過的 `swx/swy/swz` 算 3D 膝蓋角度，看哪一份比較接近（模擬中處理過的誤差少約 28%）。如果夠接近，之後正面拍也能算角度 |

每個實驗錄完後，可以把 JSON 丟進網站的「錄製資料重播分析」（`replay.html`），直接看角度曲線、拍攝方向和抖動大小，不用自己用 Excel 畫圖。

組員版的步驟（含示意圖）在網站的使用說明頁「驗證實驗」一段（`help.html#experiments`）。

**實驗 D、H 不用自己算**：重播分析頁的「3D 檢查」卡片會直接列出：

- 大腿、小腿的 3D 長度（整段的中間值）和變動大小，原始、處理過各一份；填入捲尺量的長度後，改成顯示「和捲尺差幾公分」，比較好的那一份標綠色（實驗 D）
- 側面拍的格子：3D 膝蓋角度和畫面角度（側面時很準，當標準答案）平均差幾度（單支手機就能做的實驗 H 簡化版）
- 正面拍（實驗 H 的正面那支）：按曲線圖的「3D 膝角」看曲線；兩支手機的檔案各下載「角度 CSV」，裡面有 `left_knee_3d_raw`、`left_knee_3d_stable` 等欄位，對齊時間後和側面那支的 `left_knee` 比較

重播頁的「處理過」是用和錄製時相同的程式（`js/skeleton/world.js`）從原始 3D 座標重算的，所以 2026-10 以前錄、沒有 `swx` 欄位的舊檔案也能比較。合成示範資料的大腿、小腿實際長度是 40 公分，深度加了模擬雜訊，可以先用來看這張卡片怎麼讀。

實驗 D、E 最重要：如果 3D 座標在不同距離下都一致、深度誤差可接受，之後就能改用 3D 計算角度，不再限制只能從側面拍。
